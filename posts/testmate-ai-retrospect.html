AI 生成的代码，我能讲清楚吗？——TestMate AI 项目复盘

2026-09-22 · CodeCat

这是一个很真实的问题。我的项目 TestMate AI 大部分代码是 AI 辅助写的，但我需要证明：我理解每一行代码背后的决策。

这篇博客就是证明。

这个项目是什么

TestMate AI 是一个智能测试用例生成工具。测试工程师输入一段功能需求文字，AI 自动生成标准化的功能测试用例，可以导出 Excel 文件。

一句话定位：输入需求文字，一键生成功能测试用例。

我学到的 3 件事

1. LangChain 的 ChatOpenAI 可以指向 DeepSeek

核心就这几行代码：

llm = ChatOpenAI(
    api_key=DEEPSEEK_API_KEY,
    base_url=DEEPSEEK_BASE_URL,  # 指向 DeepSeek 而非 OpenAI
    model="deepseek-chat",
    temperature=0.3
)

原理很简单：DeepSeek 兼容 OpenAI API 格式，所以 LangChain 的 ChatOpenAI 类不需要改任何代码，只需把 base_url 指向 DeepSeek 的地址。

这教会我一个概念：接口兼容性（Interface Compatibility）。一个设计良好的接口层，可以让你在不改业务代码的情况下切换底层实现。

2. AI 返回不稳定？必须有重试机制

AI 不保证 100% 返回正确格式。有时候它会返回一段带说明文字的 JSON，有时候直接超时。我的解决方案：

max_retries = 2
for attempt in range(max_retries):
    try:
        cases = generate_cases(request.requirement)
        return {"code": 200, "data": {"total": len(cases), "cases": cases}}
    except json.JSONDecodeError:
        # AI returned non-JSON
        if attempt < max_retries - 1:
            time.sleep(2)
            continue
        return {"code": 500, "message": "AI返回格式错误"}
    except (ConnectionError, TimeoutError, OSError):
        if attempt < max_retries - 1:
            time.sleep(2)
            continue
        return {"code": 503, "message": "AI服务不可用"}

这个重试机制的设计思路：

  • JSON 解析失败 → AI 返回了内容但格式不对 → 重试一次，可能这次就好了
  • 连接/超时错误 → 网络问题或 AI 服务挂了 → 重试一次，不行就告诉用户"服务不可用"
  • 状态码区分 → 500 是 AI 的锅（格式错误），503 是基础设施的锅（服务不可用）

这是生产级思维——任何依赖外部服务的系统，都必须有兜底方案（fallback）。

3. JWT 鉴权：bcrypt + JWT 的组合

用户密码不能明文存储。流程是这样的：

# 注册：密码 → 哈希
hashed = bcrypt.hashpw(
    password.encode('utf-8'),    # 字符串转字节
    bcrypt.gensalt()              # 随机盐值
).decode('utf-8')

# 登录：验证密码
bcrypt.checkpw(
    plain_password.encode('utf-8'),
    hashed_password.encode('utf-8')
)

# 登录成功后发 JWT Token
payload = {
    'sub': str(user_id),  # 用户ID
    'exp': expires         # 7天后过期
}
token = jwt.encode(payload, JWT_SECRET_KEY, algorithm="HS256")
bcrypt 就像一个单向绞肉机——你把肉放进去变成肉馅，但不可能从肉馅还原出原来的肉。这就是不可逆哈希（irreversible hash）。

JWT 的作用是让用户登录后拿到一个"通行证"，之后每次请求带着这个通行证，后端 decode 一下就知道你是谁，不用每次都查数据库验证密码。

数据隔离：用户 A 看不到用户 B 的数据

历史记录查询时，始终带上 user_id 过滤：

records = db.query(CaseRecord)
    .filter(CaseRecord.user_id == current_user.id)
    .order_by(CaseRecord.id.desc())
    .offset(offset)
    .limit(size)
    .all()

如果有人试图访问别人的记录？直接返回 403：

if record.user_id != current_user.id:
    raise HTTPException(403, "无权访问该记录")

Excel 导出：内存中生成文件流

不用临时文件，直接在内存里生成 Excel，用 StreamingResponse 返回：

output = io.BytesIO()
wb.save(output)
output.seek(0)

return StreamingResponse(
    output,
    media_type="application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
    headers={"Content-Disposition": f"attachment; filename*=UTF-8''{quote(filename)}"}
)

中文文件名有个坑：HTTP 头只允许 ASCII 字符，中文文件名必须用 RFC 5987 编码（filename*=UTF-8''），否则浏览器下载的文件名会乱码。

部署

  • 后端：部署在 Render，用 MySQL 做生产数据库
  • 前端：部署在 Vercel，自动构建 Vue 3
  • CORS：FastAPI 配置了 Vercel 域名的跨域允许
  • 环境变量：DeepSeek API Key、JWT 密钥、数据库 URL 都通过环境变量读取，不硬编码

AI 帮我写了代码，但我学到了什么

诚实地说：大部分代码是 AI 辅助生成的。但写这篇博客的过程，逼着我回答了这些问题：

  • 为什么用 DeepSeek 而不是 OpenAI？（成本，兼容性）
  • 为什么重试 2 次而不是 3 次？（平衡延迟和成功率）
  • 为什么用 JWT 而不是 Session？（无状态，适合前后端分离）
  • 为什么用内存流而不是临时文件？（避免磁盘 IO，更适合云部署）

能回答这些问题，才算"拥有"这个项目。VibeCoding 时代，能讲清楚代码的人比能写代码的人更有价值。
